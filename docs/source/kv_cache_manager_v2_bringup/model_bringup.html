KV Cache Manager V2 — Model Bring-Up Coverage

Model-centric coverage plan for KVCacheManagerV2. Complements the gap matrix (kv_cache_v1_v2_gap_20260512.pdf) by organizing work along model archetypes.

This document tracks the model-centric coverage plan for KVCacheManagerV2 (the pure-Python, mypyc-compilable replacement for the C++ KVCacheManager). It complements kv_cache_v1_v2_gap_20260512.pdf (the per-feature gap matrix) by organizing work along model archetypes rather than features, so we can land bring-up evidence one model at a time and surface integration bugs that the unit-level matrix misses.

  • V1: KVCacheManager in tensorrt_llm/_torch/pyexecutor/resource_manager.py:303 — wraps tensorrt_llm.bindings.internal.batch_manager.KVCacheManager (C++).
  • V2: KVCacheManagerV2 in tensorrt_llm/_torch/pyexecutor/resource_manager.py:1807 — wraps tensorrt_llm.runtime.kv_cache_manager_v2.KVCacheManager (Python).
  • Toggle: KvCacheConfig.use_kv_cache_manager_v2 (see llmapi/llm_args.py:2626). V2 is auto-selected for Gemma4 hybrid (per-layer head_dim) regardless of the flag (_torch/pyexecutor/_util.py:67).

1.0 V1 ↔ V2 architectural deltas (lens for everything below)

The §1 feature matrix is a what-is-supported view. This subsection is the what-is-architecturally-different view. When a model works on V1 but regresses on V2 — or vice versa — the bug almost always lives on one of these axes, not in the model code itself. Cite this table from PR descriptions and bug reports so the reader can find the implicated subsystem fast.

1. Feature Interactions with the KV Cache Manager

The KV cache manager owns block allocation, eviction, prefix reuse, multi-tier storage, and per-sequence life-cycle. A feature interacts with the manager when it changes any of: pool layout, block size, life-cycle policy, the radix key, the eviction order, or the scheduler's view of free capacity.

1a. Features that go through the KV cache manager (load-bearing)

These shape pool layout, lifetimes, or the radix key. Any bring-up must cover the subset that the model exercises.

1b. Features that are orthogonal to the manager (V1/V2 should be indistinguishable)

These run regardless of the choice of manager and should be tested for parity but not feared as a source of bring-up risk on their own:

  • LoRA (separate adapter system; manager only sees identical tokens).
  • CUDA graph capture / piecewise CUDA graph / torch.compile.
  • Tensor / Pipeline / Expert parallelism — except: V2 scheduler does not yet handle max-batch-size correctly under PP (known waive).
  • Weight-only / activation quantization (W4A16, FP8 weights, NVFP4 weights) when distinct from KV cache dtype.
  • Logprobs / top-k logprobs / structured output / guided decoding.
  • Overlap scheduler — except: gpt-oss-120b + Eagle3 + overlap scheduler has an H100 accuracy issue (known waive).

Orthogonal kernel backends (no direct manager coupling)

These don't read or write the KV manager and should be V1/V2-identical under load — verify by parity, but they are not bring-up risk on their own:

  • Quantization backends — weight-only, FP8 weights, NVFP4 weights (distinct from KV dtype).

2. Phase 1 — GPT-OSS-120B (Starting Model)

2a. Why this model

GPT-OSS-120B is a pragmatic V2 starter because it stresses the manager but avoids the V2 hard-blockers:

  • Sliding window every other layer + attention sinks (modeling_gpt_oss.py:84,115) — exercises AttnLifeCycle with windowed + sink-token policy.
  • MoE with multiple backends (Cutlass / TRTLLM / Triton) — orthogonal to KV manager but the most common GPT-OSS perf knob.
  • MXFP4 weights + optional FP8 KV dtype — covers the bytes-per-token math.
  • Eagle3 one-model spec dec is available (SpecDecOneEngineForCausalLM) — exercises draft-token flow through the same pool.
  • No beam search, no disagg requirement, no mandatory connector, no mamba state — so we avoid every V2 hard-fallback.
  • An existing parametrized harness (tests/integration/defs/accuracy/test_llm_api_pytorch.py:5314 TestGPTOSS.test_w4_1gpu) already runs with v2_kv_cache=[True, False].

3. Phase 2 — Multi-Modal Models (Recommended Next)

Multi-modal models push two manager-specific concerns that pure-text models do not: (a) image/audio tokens must be salted into the radix key (gen_multi_modal_tokens) or prefix reuse silently produces wrong outputs across different images with identical text prompts; (b) vision encoders often produce very long visual-token prefixes that stress eviction and host offloading.

Recommended bring-up order (most-coverage-per-risk first):

RankModelWhat it specifically validates
1Qwen2.5-VL-7B / 32B / 72BImage+text prefix reuse path; long visual prefixes; well-supported in TRT-LLM; mature accuracy baselines. The cleanest "does V2 multi-modal radix actually work" test.
2Llama-3.2-Vision (Mllama) 11B / 90BCross-attention KV (encoder output → cross-attn cache) — different cache topology than self-attn-only models. Currently uses cross_kv_cache_fraction; tests V2's handling of a second logical pool.

5. Known Issues Inherited from the Gap Doc
